## 4. 收尾中修掉的缺陷

### 4.1 ★ `src/utils/stageScope.ts` —— 列限定名被污染（会 `Unknown column`）

原实现把**传入的表名**直接拼成列限定名：

```ts
const col = `${opts.table}.${opts.column || defaultColumnOf(via)}`;   // → "t_job_class.head_teacher_id"
```

这在「开关关」时是对的（外层 FROM 就是 `t_job_class`）；但**开关打开后外层 FROM 已换成
`t_uni_class`**，而列限定名还写着 `t_job_class.xxx` → `Unknown column 't_job_class.head_teacher_id'`。

**修法**：新增 `refOf(opts)` 内部转调 `tblRef(dbName, table)`：

```ts
function refOf(opts: { table: string; dbName?: string }): string {
  return opts.dbName ? tblRef(opts.dbName, opts.table) : opts.table;
}
```

`tblRef()` 的语义是「开关关→原表名，开关开→统一表名」，所以**开关关时逐字节等价**。
7 个调用点补齐 `dbName`：`empDorm.route.ts` ×3、`employmentLog.route.ts:90`、
`examScore.route.ts:163`、`feeCall.route.ts:187`。

### 4.2 ★ `src/class-jh/middleware/dataScope.ts` —— 扫描脚本扫不到的隐藏裸访问

```ts
// 原：db(classTable) —— classTable 是**变量**
const rows = await base.where('is_deleted', false).andWhere(...).select('id');
```

表名走变量 → `_uni-bare-scan.mjs` 这类**正则扫描器一律扫不到**；
而它的两个调用方（`class-jh/routes/student.route.ts:247`、
`teaching/student/repo.classJh.ts:111`）**早已切读** →
开关打开后会在「算班级数据范围白名单」这一步**静默绕回老表**，导致
「列表按老表过滤、明细读统一表」的错配。

**修法**：新增可选参数（不传 = 原样，开关关行为不变）：

```ts
export async function getScopedClassIds(
  db: any, classTable: string, scope: ClassScope,
  dbName?: string, stage: TeachingStage = 'jh',
): Promise<string[] | null> {
  if (!scope.isClassScope || !scope.userId) return null;
  const base = dbName ? tbl(db, dbName, classTable, stage) : db(classTable);
  ...
```

### 4.3 ★ `UNI_MAP` 里一条指向**不存在老表**的错误登记

`'sms_class_jh.t_class_approval_log': 't_uni_approval_log'` —— 实测
**`sms_class_jh.t_class_approval_log` 这张表不存在**（初高的审批流水表是
`t_class_flow_log`，已在 `UNI_MAP` 第 457 行登记）。

该条目由新脚本 `scripts/_uni-callsite-audit.mjs` 的「(库,表) 在真实库里不存在」检查抓出。
`assertUniMapConsistent()` **只比对两份副本的 key 是否一致**，
**查不出「key 指向的老表不存在」** → 错映射必须靠库核对删除，
否则会误导后来人写出「老表挂、切读绿」的代码。

**修法**：`uniTable.ts` 删除该条 + 写长注释说明「为什么留着无害是错的」；
`scripts/_e2e-lib.mjs:329` 同步删除。

### 4.4 `finance/services/class-sync.ts` 的跨库 runner 类型不兼容

`finance/utils/db.ts` 导出的 `db` 是「带表名校验的函数 + 挂在函数上的静态成员」，
不是 `Knex` 实例 → `tbl(CONN, ...)` 静态类型不通过。
用纯类型断言解决（**不改运行时行为**）：

```ts
const CONN = db as unknown as Parameters<typeof tbl>[0];
```

## 5. #21（T3）· 统一表缺失老表已有的唯一键 —— **19 处** ★

### 5.1 性质

**正向**（T1/#18，已处理）：统一表**凭空多出**唯一键 → 「先软删再 insert」撞 `Duplicate entry`。
**反向**（本项）：统一表**丢了老表本来就有的**唯一键 → 依赖它的
`ON DUPLICATE KEY UPDATE` / `knex.onConflict().merge()` **定位不到索引 →
静默退化成普通 INSERT → 插出重复行**。

### 5.2 判定脚本

`scripts/_uni-uniquekey-audit.mjs`（已把双向检查并入同一个脚本，常驻）：

```bash
node scripts/_uni-uniquekey-audit.mjs
```

判据：老表唯一键 `lu`（排除 PRIMARY）；若统一表的所有唯一键里**不存在一条 `uk` 使
`uk.cols ⊇ lu.cols`（超集）** → 判为「未覆盖」。
例：`sms_class_jh.t_class_student.uk_student_no(student_no)` 被
`t_uni_student.uk_student(student_no, edu_stage)` 覆盖 → **不算**。
