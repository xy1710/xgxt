### T1（任务 #18）· 排查 `class/modules/*` 的「软删 + 唯一键」隐患

**背景**：P2 在 `src/class/modules/attendance/attendance.route.ts` 发现并修复了一个真缺陷——
代码「先把旧明细整体软删 `is_deleted=1`、再 `insert` 新行」，在老表上一直"看起来正常"，
但切读后的统一表 `t_uni_attendance_detail` 有**唯一键** `uk_attendance_detail(attendance_id, student_id, edu_stage)`，
软删行仍占唯一键 → 必报 `Duplicate entry`。这批 route 都已切读，属**现网隐患**。

**范围**：`src/class/modules/` 下 10 个 route 文件（attendance 已修）
```
approval / class / consult / dorm / exam / fee / grade / student / urge / notify
```

**做法**（每个文件）：
1. 搜「`update({ is_deleted: 1 })` … 紧接 `insert(`」的模式；
2. 查目标 `t_uni_*` 的 `information_schema.statistics`：是否有 `non_unique=0` 且列组合覆盖同一业务键；
3. 对照**老表**同表是否有该唯一键（老表通常只有普通索引）——**只有「新表有、老表没有」才是隐患**；
4. 命中 → 改成**按业务键 upsert**（已存在则原地 update 并把软删行复活；未提交的逻辑删除）。

**★ 附带产出**：新增常驻脚本 `scripts/_uni-uniquekey-audit.mjs`，自动输出
「统一表有唯一键、但对应老表没有」的表清单 → 这是同类隐患的**高危点索引**，可反复复扫。

**验收**：10 个文件每个给出结论（无风险 / 已修）；`_e2e-class-check.mjs` 保持 80/80、`_e2e-class-four-check.mjs` 27/27。
