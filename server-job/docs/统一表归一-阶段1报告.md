## 一、T1 · 「软删 + 唯一键」隐患清零（#18）

### 1.1 这个隐患类是什么

统一表上的**唯一键**（如 `uk_attendance_detail(attendance_id, student_id, edu_stage)`）是刻意的业务约束。
但代码里存在两种会撞它的写法：

| 写法 | 后果 |
|---|---|
| **A. 一次操作内「先整体软删、再逐条重插」** | 软删行仍占唯一键 → `Duplicate entry` |
| **B. 重复校验漏算软删行**（只查 `is_deleted: 0`） | 「查着不重复、插入却报错」，用户现象是「删了就再也建不出来」 |

老表**只有普通索引**，这两种写法一直"看起来正常" → 属「老表宽松掩盖了代码缺陷」。

**项目既有约定**（`teaching/dorm/repo.uni.ts:318` 早已写明）：
> 唯一性检查必须**把软删记录算进去**……否则「这个房间明明删了，却再也建不出来」，而且越删越死。

本轮新增的修复一律遵循这条既有约定，不另发明机制。

### 1.2 新增两个常驻审计脚本

| 脚本 | 作用 |
|---|---|
| `scripts/_uni-uniquekey-audit.mjs` | 列出「统一表有唯一键、而其老表源表全都没有等价唯一键」的表 → **隐患高危点索引** |
| `scripts/_uni-bulk-softdel-scan.mjs` | 扫全仓 `is_deleted=1` 的写法，区分「批量软删（where 不含 id）」与「按主键软删（安全）」 |

审计结论：**10 张高危表** —— `t_uni_approval`、`t_uni_attendance_detail`、`t_uni_class`、`t_uni_class_student`、`t_uni_dorm_apply`、`t_uni_dorm_room`、`t_uni_exam`、`t_uni_exam_content`、`t_uni_refund`、`t_uni_refund_item`。

### 1.3 本轮修掉的 4 个真缺陷

#### ① `teaching/exam/repo.class.ts::save()` —— 考试内容（★ 与 P2 出勤同款）
- **原写法**：编辑考试时 `update({is_deleted:1}).where({exam_id}).update(...)` 后逐条 `insert`
- **为什么会炸**：`t_uni_exam_content` 有 `uk_exam_content(exam_id, exam_content_type, edu_stage)`；
  老表 `t_class_exam_content` 只有 `idx_ec_exam(exam_id)` 普通索引
- **改法**：按 `(exam_id, exam_content_type)` **upsert** —— 已存在（含软删）原地更新并复活；本次未提交的旧项逻辑删除
- 附带把两处 `.insert()` 换成 `tblInsTrx()`（统一 edu_stage 注入与 NOT NULL 兜底）

#### ② `class-jh/routes/attendance.route.ts::/import` —— 初高出勤（P4 潜伏 bug）
- 原注释白纸黑字写着「明细先做逻辑删除再重插（禁止物理删除）」→ **与 P2 修的出勤 bug 一字不差**
- 该文件用裸 `trx(DETAIL_TABLE)`，即便开关打开也只写老表 → 今天不炸，
  但 **P4 一接 `tblTrx()` 立刻炸**。已提前改成 upsert。
- **补了自检**（原文件无任何测试覆盖）：新增
  `scripts/_e2e-classjh-att-import-check.mjs`，**8/8 通过**

#### ③ `teaching/class/repo.{class,classJh,job}.ts` —— 建班重复校验漏算软删行
- **原写法**：`.where({ class_name, dept_code, is_deleted: false })` → 查不到软删行 → 直接 insert → 撞 `uk_class`
- **★ 其中两处在老表模式下就已经是 bug**：
  `sms_job.t_job_class` 本来就有 `uk_class_code(class_code)`、
  `sms_class_jh.t_class_info` 有 `uk_class_name(class_name)` —— 原来的过滤让它们同样"删了就建不回来"
- **改法**：按项目既有约定，**不带 `is_deleted` 条件**，并区分提示
  「已存在」vs「之前已删除过（记录仍占唯一键），不能重复使用」

#### ④ `teaching/dorm/repo.uni.ts::syncBeds` —— 床位续号撞 `uk_dorm_bed`
- **原写法**：`start = max(bed_no)` 只统计 `is_deleted: false` 的活跃床位；
  而裁剪删的是 `free.slice(0, surplus)`（**无 orderBy，顺序不保证**）→ 可能删掉编号最大的几张
- **必炸路径**：4 张床 → 裁到 2 张（删了 3/4 号）→ 再扩到 4 张 → 新增 bed_no 3、4 → 撞
  `uk_dorm_bed(room_id, bed_no, edu_stage)`
- **改法**：取号范围改用**全量（含软删）床位**的最大 `bed_no`，软删号段不再复用

## 三、踩坑记录

⚠️ **块注释内不得出现 `*/` 序列。** 本轮在 `UNI_MAP` 的说明注释里写了 `create_*/update_*`，
其中 `*/` 提前闭合了块注释 → `tsc` 报 100+ 个语法错误。已在 memory 记过同款坑（`**/`），
这次是第二种形态：**斜杠紧邻星号的任意组合都要避免**（建议写成 `create_xx / update_xx`）。

⚠️ **备份同名文件必须带路径结构。** 做「还原改动再跑」对照实验时，
把 `teaching/exam/repo.class.ts` 与 `teaching/class/repo.class.ts` 都备份成 `/tmp/_bak2/repo.class.ts`
→ 后者覆盖前者 → 恢复时把班级仓储写进了考试仓储。
所幸该文件与 HEAD 一致（无未提交改动），`git checkout HEAD --` 即完全复原，无损失。
**教训：备份路径必须保留目录层级**（如 `/tmp/_bak2/exam_repo.class.ts`）。
